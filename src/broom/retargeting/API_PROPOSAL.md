# Контракты ретаргетинга Broom

Дата: 2 октября 2026 года. Статус: актуальное описание задачи и целевого интерфейса.

Этот документ заменяет прежние варианты предложения. Примеры целевых вызовов не означают, что рефакторинг уже реализован. Отличия текущего кода перечислены в разделе 10.

## 1. Общая задача библиотеки

Broom предоставляет математические функции для переноса движения между **произвольными source и target скелетами**. Их пропорции, число joints и сегментация конечностей могут различаться. «Произвольные» не означает отсутствие требований к данным: выбранный метод имеет ограничения DOF, геометрии, систем координат и соответствий, которые нужно явно проверять или документировать.

На входе:

- source Motion — исходная иерархия и полное движение всех её joints;
- target Hierarchy — скелет, на котором требуется получить движение;
- явный source→target joint mapping;
- описание обрабатываемых source-цепочек;
- настройки переноса, пола и оптимизации, а также явно подготовленные constraints.

На выходе — новый Motion на target Hierarchy. Промежуточное движение и диагностика оптимизации остаются доступны вызывающему коду. Source, подтверждённый mapping и ранее полученные Motion не перезаписываются.

**DEFAULT_SOURCE_CHAINS — только готовый список цепочек для конкретного source skeleton.** Он экономит повторное описание одинаковых исходных анимаций. Общий алгоритм не зависит от DEFAULT, человеческой анатомии или названий joints; другой пользователь задаёт собственные цепочки для своих скелетов.

## 2. Три разных вида данных

Их нельзя смешивать:

| Данные | Что описывают | Кто задаёт |
|---|---|---|
| Source chains | Какие пути исходного скелета обрабатывать | Пользователь Broom или готовый preset |
| Joint mapping | Какие source joints соответствуют каким target joints | Подбор с последующей проверкой либо ручное задание |
| Required correspondences | Какие пары обязательны для выбранного сценария | Продуктовый preset или вызывающий код |

Joint в описании source-цепочки **не становится автоматически обязательной парой mapping**. Например, source содержит локоть и его анимацию, даже если target не содержит соответствующего локтя.

В Broom нет универсального списка обязательных плеч, ладоней или стоп. У конкретного chain-сегмента должны быть известны соответствующие границы, а у constraint — участвующие joints. Продуктовые требования могут быть строже этих математических предпосылок.

## 3. Подбор и подтверждение mapping

Каноническое направление: **source name → target name**. На текущем этапе допускается только частичный one-to-one mapping: один source joint соответствует одному target joint, один target не используется несколькими парами. **Many-to-one и one-to-many mapping не поддерживаются**; их семантика и алгоритмы требуют отдельных экспериментов. Не кодируем их последовательной перезаписью, дублированием пар или неявной агрегацией.

Разное число промежуточных joints между двумя однозначно сопоставленными концами — отдельная задача геометрической подготовки цепочек. Это не поддержка many-to-one/one-to-many joint mapping. Такой кандидат уже реализован, но его качество и область применимости при сильном изменении сегментации ещё нужно проверить; наличие функции не означает гарантированно успешный перенос любой цепочки.

`map_joints(source_hierarchy, target_hierarchy, known_joint_map=...)` возвращает предложение и confidence/reasons. `known_joint_map` фиксирует известные пары при явно запрошенном поиске; остальные могут быть предложены matcher. Confidence — оценка matching, не качества будущей анимации.

Пользователь может:

- удалить ошибочную или ненужную пару;
- изменить target joint;
- добавить пару, которую matcher не предложил из-за threshold или неоднозначности.

После подтверждения численные методы используют **ровно сохранённые пары**. Никаких auto-fill, fuzzy lookup, восстановления удалённого локтя или повторного подбора при запуске анимации. Пустой mapping не означает запрос на автоматический поиск.

`validate_joint_mapping` проверяет имена и структурную допустимость обычных пар. Требования конкретных цепочек, constraints и продуктовый required-набор проверяются дополнительно. Проверка не исправляет данные.

MappingResult и RetargetResult должны хранить согласованные снимки данных. Для ручного редактирования возвращается отдельный dict; изменение исходного словаря после вызова не должно менять уже полученный результат или рассогласовывать mapping и scores. Состояния «последний mapping» нет.

## 4. Базовый перенос со всеми настройками

Сохраняем `retarget_mapped_motion(source_motion, target_hierarchy, joint_map, ...)` как явный перенос, включая существующие параметры scale, rotation correction и floor alignment. Ради архитектурной чистоты не удаляем полезные настройки и не прячем их за сокращённой обёрткой.

- Создаётся новый target Motion с source F/frame_time.
- Переносятся поддерживаемые rotation/translation channels mapped joints; остальные target channels первоначально нулевые.
- У root→root пары текущая translation policy переносит displacement относительно первого source кадра с scale. Для остальных пар переносятся локальные translation deltas с scale.
- Floor alignment — отдельная явно выбранная операция внутри этого вызова. Она может изменить root даже вне mapping; утверждение «меняются только mapped channels» относится к переносу до этой операции.
- Системы координат и единицы согласовываются явно. Текущий `rotation_correction="rest_pose"` использует эвристические frames; он не является универсальной calibration произвольных арматур.
- Неподдерживаемые layouts не должны молча пропускаться; корректность поддерживаемого входа отделяется от будущего расширения DOF.

Автоматическая функция `retarget_motion(..., known_joint_map=...)` остаётся отдельным удобством для явно запрошенного подбора и переноса. В workflow с подтверждённым mapping используется строгий mapped-вход.

## 5. Chains: подготовка содержательного reference

### 5.1. Зачем нужны source и initial target

```python
refine_mapped_chains(
    source_motion: Motion,
    initial_target_motion: Motion,
    joint_map: Mapping[str, str],
    *,
    chains: Sequence[tuple[str, str]],
) -> Motion
```

Source содержит движение всех исходных звеньев, включая joints без прямой пары. Initial target задаёт подготовленное движение на целевой иерархии: translations, root placement и начальные rotations. Chains обрабатывает выбранные области, сохраняя остальные channel values.

Назначение — получить разумное первое приближение при разной сегментации скелетов, особенно перед space-time. Результат также можно использовать без оптимизации. Не требуется отдельный «особый» алгоритм chains исключительно для solver.

### 5.2. Описание цепочки и выделение сегментов

`chains` содержит только **пары начала и конца пути в source hierarchy**:

```python
chains = (
    ("LeftShoulder", "LeftHand"),
    ("RightShoulder", "RightHand"),
)
```

Оба конца должны иметь mapping. Полный путь, включая все промежуточные source joints, восстанавливается из hierarchy. Три и более имени в одной записи — ошибка: промежуточные соответствия задаются только в mapping, не дублируются в описании цепочек.

Реализованное правило выбора сегментов:

1. Развернуть полный source-путь между двумя концами.
2. Построить полный target-путь между их соответствиями.
3. Найти все промежуточные source joints на пути, имеющие mapping. Их target joints должны лежать на найденном target-пути в том же порядке; иначе ошибка, без игнорирования пары.
4. Разбить оба пути по этим соответствиям на согласованные сегменты.
5. Сохранить в каждом сегменте все unmapped intermediate joints и их исходное движение; никаких новых matching pairs не добавлять.

Недостающий endpoint mapping — ошибка. Продуктовый список обязательных суставов остаётся отдельным требованием. Алгоритм не заменяет отсутствующее плечо грудью/root автоматически.

Пример частичного mapping:

```text
Source: Shoulder → Elbow → Hand
Mapping: Shoulder → A, Hand → B

Target 1: A → B
Target 2: A → j1 → j2 → … → j100 → B
```

Один и тот же source branch должен работать для обоих target. Если пользователь также сопоставил Elbow, это добавляет известную границу между двумя сегментами. Удаление необязательной пары Elbow объединяет их, но не выбрасывает исходный локоть из расчёта.

DEFAULT содержит именно такое описание source-путей. Его не нужно переписывать для каждого target. Required-набор продуктового preset задаётся отдельно и проверяется до генерации.

### 5.3. Геометрическая подготовка

Реализованный математический кандидат:

1. Через FK получить движущуюся source-ломаную и глобальные orientations.
2. По rest geometry определить постоянные нормированные координаты вдоль source и target segments.
3. На source-ломаной выбрать точки в координатах target joints.
4. Направить target-звенья вдоль полученных хорд, сохраняя target длины.
5. Интерполированные source orientations использовать как reference для twist; минимальным swing совместить направление звена с желаемым.
6. Восстановить target local rotations и записать channel rotations через `Q = O.T @ R_local`.

**Вращение начала цепочки тоже меняется.** Для target «плечо → кисть» именно плечо поворачивает звено в сторону source-кисти. Ориентация конечной кисти обрабатывается отдельно от положения её joint origin.

Общий joint нескольких ветвей получает совместно согласованное вращение; правило «последняя ветка перезаписала предыдущую» недопустимо. Результат не должен зависеть от порядка chains. Точные дубликаты удаляются, конфликтующие пересечения путей отклоняются явно.

### 5.4. Что гарантирует и чего не гарантирует chains

- Новый Motion; source и initial не меняются.
- Одинаковые F/frame_time у source и initial; неявного resampling нет.
- Translation channels сохраняются. Rotations вне выбранных paths сохраняются, но глобальные позы их потомков могут измениться.
- Длины target не подгоняются под source. Точное попадание в source endpoint при другой геометрии не гарантируется.
- Направления плюс orientation reference не гарантируют отсутствие всей потери информации при уменьшении DOF.
- Пока требуются согласованные world axes/frames, поддерживаемые rotation channels и невырожденные пути; нулевые звенья, схлопнутые хорды и неоднозначности twist требуют явной политики.
- Chains не извлекает contacts, не оптимизирует constraints и не выполняет floor alignment.
- Сохранение translation channels не сохраняет world positions стоп: вращения ног или корпуса могут сместить их по всем трём координатам.

Численные проверки на маленьких примерах подтверждают отдельные свойства примитива, а не качество общего ретаргетинга на произвольных реальных анимациях.

### 5.5. Удобный полный вызов

Существующий `retarget_mapped_chains` может оставаться короткой композицией переноса и refinement. Он не должен быть единственным доступным способом использования chains. Если его параметры не покрывают нужные настройки переноса, вызывающий код использует полный `retarget_mapped_motion` и затем `refine_mapped_chains`; никакие возможности исходного переноса при этом не теряются.

## 6. Constraints и пол

Source-derived требования строятся по **оригинальному source Motion**, а не по initial или refined target Motion:

- моменты контактов стоп и других действий — из source либо явно заданы пользователем;
- relational distances и activation — из source;
- target joint names — из подтверждённого mapping;
- плоскость пола, target-space позиции контактов, scale и преобразование координат — из выбранных настроек target-сценария.

Не нужно копировать абсолютные source positions в другую геометрию без определения политики переноса целей. Определение контакта и выбор target contact position — разные действия.

Для relational builder предлагается единый source→target mapping и явный набор source pairs. Это целевое изменение: сейчас builder ещё принимает `role -> (source, target)`. Пропавшая выбранная пара должна давать понятную ошибку; новые пары не угадываются.

Нормированные расстояния между joint origins не равны контакту поверхностей ладоней. Их ограничения качества не меняют правило: хлопок определяется исходным движением, а не положением рук после переноса.

Начальное floor alignment и ограничения оптимизации различаются:

- после chains можно снова выровнять reference по заданному полу;
- floor constraint запрещает/штрафует проникновение, но сам по себе не удерживает стопу на поверхности;
- отсутствие скольжения и высоту во время контакта задают соответствующие stationary/position требования;
- автоматический сдвиг после solver может нарушить уже выполненные цели, поэтому его не включаем молча.

Контактный builder и формат продуктового выбора контактов не объявляются реализованными этим документом.

## 7. Space-time: полноценная функция с явным контрактом

Целевой основной вход после рефакторинга:

```python
retarget_motion_spacetime(
    reference_motion: Motion,
    constraints: Sequence[Mapping[str, object]],
    *,
    control_point_spacing: int = 4,
    control_weight: float = 1.0e-3,
    parameter_weights=None,
    constraint_tolerance=DEFAULT_CONSTRAINT_TOLERANCE,
    smoothing_sigma: float = 1.0,
    max_nfev: int | None = None,
    ftol: float = 1.0e-6,
    xtol: float = 1.0e-6,
    gtol: float = 1.0e-6,
    verbose: int = 0,
) -> OptimizeResult
```

Это реализация оптимизации с явно объявленными настройками, **не обёртка с непрозрачным `**solver_options` над другой публичной функцией**. Target hierarchy находится внутри reference. Original source hierarchy и scale переноса не нужны: reference и constraints уже подготовлены в target space.

Сохраняются Motion, solver status, residuals, control points и фактические initial_motion_values в результате. Не урезаем возвращаемую диагностику ради единого return type с другими этапами.

Текущая математика:

```text
Q_result(t) = Q_reference(t) @ Exp(delta(t))
delta(t) задаётся B-spline
objective = штраф величины поправок + взвешенные ошибки constraints
```

Сплайны обеспечивают гладкую во времени поправку. Reference остаётся основой движения и регуляризации. Нулевые rotation channels reference не блокируют оптимизацию этих joints. Если constraints уже выполнены, нулевая поправка может оставить исходные рывки нетронутыми. Ограничения здесь мягкие, поэтому solver success не означает точного выполнения всех целей.

Перед итерациями position constraints сейчас могут вызвать root-centering; `smoothing_sigma` относится к подготовке этого сдвига. Это поведение нужно сохранить/явно описать при выделении solver, а не потерять вместе со старой сигнатурой. Tolerance выражается в согласованных target length units; число само по себе не задаёт физические миллиметры без соглашения о units.

Старый проверенный equal-topology сценарий должен сохранить свою подготовку reference в регрессионных проверках. Не заменять её незаметно новым mapped transfer: scale/rebase могут различаться. Legacy-совместимость публичных имён не обязательна, но численно проверенное поведение нельзя потерять из-за переноса кода.

## 8. Продуктовый preset и два этапа использования

### Настройка арматуры

Продуктовый preset содержит описание source chains, required correspondences, настройки переноса и выбора constraints. Например, плечи, ладони, таз и стопы могут быть обязательными; **точный список должен быть зафиксирован продуктом**, а не угадан в Broom. Остальные пары допускается не задавать.

1. Плагин переводит Blender armature в joint-based Hierarchy.
2. Matcher предлагает пары с confidence. DEFAULT — source skeleton именно этого продукта.
3. Пользователь исправляет, удаляет и добавляет пары, включая оставленные matcher пустыми.
4. Перед подтверждением проверяются required-набор и пригодность выбранных chain paths/DOF. Отсутствующее обязательное соответствие предлагается заполнить; грудь не подставляется вместо плеча автоматически.
5. Сохраняются подтверждённые пары и их привязка к версии source preset, target rest skeleton и calibration.

Пользователь видит привычную арматуру, а не различие bone-based/joint-based. Извлечение evaluated pose, roll, object transforms, единицы/оси, обратный bake и отображение технических joints принадлежат Blender-адаптеру.

### После генерации

С сервера приходит source Motion. Исполняющий код использует уже подтверждённый mapping и preset, без нового угадывания:

```text
source + target + confirmed mapping + настройки
    → обычный mapped transfer
    → chain refinement с исходным source
    → при необходимости повторное размещение reference на полу
    → space-time с constraints из оригинального source в target space
    → output Motion → Blender bake
```

Целевой пример численной части; новый контракт chains и одноаргументный space-time ещё требуют реализации:

```python
initial = retarget_mapped_motion(
    source_motion, target_hierarchy, confirmed_mapping,
    scale=chosen_scale,
    rotation_correction="none",  # Предполагает согласованные frames.
    floor_height=floor_height,
    floor_up_axis="Y",
)
reference = refine_mapped_chains(
    source_motion, initial, confirmed_mapping,
    chains=source_chains,  # DEFAULT preset или собственное описание.
)
reference = align_root_to_floor(reference, floor_height=floor_height, up_axis="Y")

# constraints отдельно подготовлены по original source и настройкам target.
result = retarget_motion_spacetime(
    reference_motion=reference,
    constraints=constraints,
    control_point_spacing=4,
    control_weight=1e-3,
    max_nfev=100,
)
output_motion = result.motion
```

Повторное floor alignment — выбранная здесь политика, не обязательный эффект chains. Когда оно выполняется после chains, начальное выравнивание можно пропустить. Доступны все промежуточные Motion и полная диагностика; каждый этап можно использовать отдельно.

Объединяющий код может находиться в Broom, плагине либо частично в обоих. Это решение о поставке продукта; оно не меняет общие математические контракты. Не требуется ни единый pipeline class, ни перенос всей продуктовой логики в библиотеку.

## 9. SMPL-X и организация модуля

SMPL-X остаётся в `adapters`: преобразует joint-based Motion в другое представление и сериализуемые параметры. Одна пользовательская поза представляется однокадровым Motion; для этого не требуется chains или space-time. Подтверждённый mapping может участвовать в явной композиции соответствий к SMPL-X. Calibration и маска пользовательских ограничений — отдельные данные.

Проверку канонической SMPL-X topology и корректности calibration matrices пока допустимо оставить требованиями к пользователю. FPS остаётся на рассмотрении; этот документ не предписывает его менять.

Сохраняем обычные функции и существующие файлы: `mapping.py`, `retarget.py`, `chain_retarget.py`, `relational_constraints.py`, `spacetime.py`, `adapters/smplx.py`. Общие helpers используют rotations/kinematics; зависимости от исследовательского analysis не вводятся.

Результаты соответствуют задачам: MappingResult — предложение, RetargetResult — автоматический перенос, Motion — mapped/chain операции, OptimizeResult с Motion — space-time. Не требуется искусственный общий контейнер или скрытое состояние Retargeter.

## 10. Что ещё не соответствует целевому описанию

По текущему коду, просмотренному при обновлении документа:

- Геометрический `refine_mapped_chains` уже существует: использует source-позиции и orientation reference, вращает начало, снимает O при записи и согласует общие ветви. Выделение сегментов обновлено: `chains` принимает пары концов, промежуточные соответствия берутся из mapping. Preset переименован в `DEFAULT_SOURCE_CHAINS` и содержит только пары концов; прежний аргумент `branches` удалён.
- `retarget_mapped_chains` — ограниченная convenience-композиция. Полные настройки переноса доступны через отдельный `retarget_mapped_motion`, затем refinement. Floor настройки базового переноса сохраняются.
- `build_relational_constraints` ещё принимает прежний semantic mapping. Его переход к общим парам не реализован этим документом.
- `retarget_motion_spacetime` ещё имеет два Motion на входе и equal-topology подготовку. `solve_motion_spacetime` передаёт один reference дважды через `**solver_options`. Их нужно привести к одному полноценному оптимизационному входу с явными параметрами, сохранив численную подготовку/диагностику.
- Required product correspondences пока не заданы окончательным списком. Не превращать примеры анатомических ролей в неявный универсальный контракт.

Необходимые проверки при реализации: удаление необязательного elbow mapping с сохранением его влияния в source-геометрии; разная сегментация слева/справа, в том числе одно и много target-звеньев; собственный source preset без DEFAULT; ошибка при нехватке необходимых границ; добавление промежуточной пары без auto-fill; совместимость source-derived constraints с target reference; независимость от порядка chains и неизменность входов. Отдельно сохранить регрессию прежнего equal-topology space-time сценария.

Наведение порядка в интерфейсе не означает завершения исследования качества. Оценку на реальных клипах, улучшение контактов, сложных calibration и вырожденных цепочек проводить отдельно от этой правки документации.


### Проверка подготовки reference
